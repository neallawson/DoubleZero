# Purpose

DoubleZero is an app for tracking and managing soccer teams, players, personnel,
games, and more. It features authenticated CRUD screens (with soft deletes) for
all domains and a RESTful API for integration with the frontend, the mobile client,
and potentially other apps/services at some point.


# Overview

The DoubleZero project is a web and mobile application that is built with the
following technologies:
 * Node.js (for the server)
 * Express Server (for the server)
 * Typescript (for the coding language)
 * Svelte Kit for the frontend
 * Tailwind CSS (for styling)
 * ZOD for validation
 * Mobile: Either Svelte Native or Capacitor (TBD)
 * MariaDB (for the database)


# Code Architecture/Layout

/src/backend/ - for the Express backend, API, service layer, model layer, etc.
/src/frontend/ - for the Svelte frontend, components, etc.
/src/mobile/ - for the mobile app, components, etc.
/src/shared/ - any shared components or utilities.


# Features

Backend API that is authenticated and supports the following:
- Use Express.Router for clean route separation.
- a Static router to serve files from the public directory.
- Default router for authentication. Displays login page or redirects
 to user's dashboard. Login page includes registration.
- Role-Authenticated CRUD operations for all domains

For managing player positions in general and for specific games frontend uses a soccer
field motif/image to display the field and the players on the field. The coach can drag
and drop the players to the field to indicate their positions. In a side panel is a list
of remaining players that can be added to the remaining positions. This helps the coach
plan the game. Once saved, a roster can be generated for the game for printing, email, etc.

On login, the user is redirected to a dashboard that shows several cards, based on
the user's role:
- a calendar of games
- current season stats
- current team stats
- current player stats (if PLAYER)
- player roster (if PLAYER, HEAD_COACH, COACH, MANAGER)

# Security

The application is authenticated (possibly using the Better-Auth library?) with local
accounts in the database and local authentication to start. It eventually must support
other authentication methods, such as Google, Facebook, etc., so this needs to be
flexible enough to support that from the start.

Practical Usage Notes
Soft deletes (isDeleted) and activity flags (isActive) help with audit history.

Role scoping via scope_type makes permissions adaptable.

Team rosters are seasonal; historical data is preserved on transfers.

Game events record time, actors, affected users, and details—enabling advanced match logs and analytics.

Stats tables allow for rapid querying of leaderboards and player stats.

The structure supports features like scheduling, announcements, and notifications.

Here’s a versioned RESTful API concept for the DoubleZero soccer app, compatible with your enhanced, normalized database schema.
It covers full CRUD (using soft deletes), pagination, role-based access, and extensibility for future features. This design
balances maintainability with ease of use—for both web/mobile clients and integrations.

API Versioning
All routes start with /api/v1/* (or /v1/*), making upgrades non-breaking:


GET /api/v1/users
POST /api/v1/games
...
Common Patterns for All Endpoints
Pagination:

All GET list endpoints accept ?page=, ?limit=, optionally ?sortBy=, ?order=.

Responses include: totalCount, page, limit, and results array.

Soft Deletes:

Instead of hard DELETE, all records have isDeleted (and often isActive).

DELETE sets isDeleted=true; GET endpoints exclude deleted by default, but may include with a query (?includeDeleted=true).

Audit Fields:

created_by, updated_by are set by auth context.

Authentication & Permissions
JWT or session-based.

Roles provided per UserRole table; scoped permissions (global/league/team/game).

Some endpoints (e.g., admin updates) restricted by role.

Soft Deletes Implementation
All DELETE endpoints set isDeleted: true (and isActive: false if applicable).

Update timestamps and audit (updated_by) on soft-delete.

All normal GET endpoints exclude deleted records unless an admin uses ?includeDeleted=true.

CRUD and Edit Patterns
POST creates (returns resource with ID and timestamps).

PATCH for partial updates (including reactivation: isActive: true).

No PUT, unless you want full replacements.

Bulk endpoints:
Where appropriate, batch POST, PATCH, or DELETE can be implemented for management (e.g., roster updates).

Error and Status Codes
200 OK on successful GET

201 Created on success POST

204 No Content for successful DELETE (soft)

400 Bad Request for invalid data/payloads

403 Forbidden for unauthorized access/role violation

404 Not Found for invalid resource ID

Validation errors include field detail in JSON

Notes for Implementation
Endpoints grouped by entity; versioned for upgrade safety.

Soft deletes used everywhere, preserving data for compliance and audit.

Granular, scope-based role permissions using roles assigned in context.

Pagination standard for all listings.

Future extensions: Push notifications, game conflict checks, external stats feeds, etc., can add endpoint groups as stable for v1 and as /v2 as needed.
