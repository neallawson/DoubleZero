Schema Changes Summary (v2)

✅ New in v2

  • league.active_season_id - League's official current season (set by league admin)
  • team.active_season_id - Team's working season (can lag behind league for data entry)
  • locker_room.team_id + locker_room.season_id - Locker rooms are now per-team-per-season
  • game_participant.is_captain - Captains are game-specific (moved from team_member)
  • app_config table - Key/value store for system-wide settings
  • user_session_state table - Per-session state including activeTeamId (cascade deletes with session)

❌ Removed in v2

  • team.locker_room_id - FK inverted; locker_room now points to team
  • team_member.is_captain - Moved to game_participant (captains are per-game)

🔄 Key Design Decisions

  • Two-level active season:
    • league.active_season_id = official current season
    • team.active_season_id = team's working season
    • If they differ, show warning banner to team users
  • Season-specific locker rooms:
    • Each team gets a new locker room each season
    • Old locker rooms become read-only archives
    • "Start New Season" button creates new locker room + updates team.active_season_id
  • Team persists across seasons - Team identity is permanent; membership and locker rooms are season-specific
  • Captains are game-specific - The armband can change game-to-game
  • Game participants via team_member - Enforces that only team members can participate
  • Game events via game_participant - Enforces that only participants can have events
  • Officials are separate - Referees use game_official table, not game_participant

📋 Season Transition Flow

  1. League admin creates new season
  2. League admin sets league.active_season_id = new season
  3. Teams with old active_season_id see warning banner
  4. Team admin clicks "Start New Season" when ready
  5. System creates new locker room for team + season
  6. System updates team.active_season_id
  7. Team admin configures new season's roster (team_member records)
