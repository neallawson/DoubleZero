I'd like to add a "create roster/lineup" screen that helps a coach populate all of the game_participants for a given team on one screen.
To access this new screen, there will be a button on the "New Game / Edit Game" screen under each of the two team select boxes.
The buttons are disabled until the record is saved (we'll need that game id). Clicking on the button for a given team does the following:

- brings up a screen that is a table of all the players on that team, one player per row. Each player has a select box for their position.
 For players with a default position (teamMember.postitionId), the select box defaults to that position. To the right of the select box
 is a checkbox for whether or not this player will be on this game's roster. By default, all the checkboxes are checked. Unchecking a player
 will remove them from this game's roster when saved. When saved, we have all of our player/positions to create the game_participants for
 this team and game.

 The coach creating/editing the game can then click on the "Create roster" button underneath the other team and perform the same actions 
 on their members to set the roster for that team.

 This suggests that we need an "owner" for the game record. The owner is the team that created the game, and TEAM_ADMIN users for that team can
 edit the game including the rosters for both teams.

  Thoughts on the interactive soccer field - PlayBoard.
  - The "Playboard Composor" is an interactive editor used to compose scenarios on the field.
  - The Playboard Composer creates entites called "Plays" that are saved to the database.
  - The Playboard Composor has a "View" or "Run" mode that is an interactive viewer used to view
  saved and composed scenarios on the field.
  - The Playboard Composor has a "Create" mode that is an interactive editor used to create
  new scenarios on the field.
  - top down and oblique views of the field - ability to tilt and rotate field will help especially with mobile.
  - green field with proper white lines (or correct colors) in the correct locations.
  - players are team-colored icons with visible number. Touching/holding a player will pop up a small card with the player's name and position.
  - players can be dragged and dropped around the field to new positions.
  - To keep the positions accuracate on multiple devices, we will define a world coordinates system for the field
  and map that field to the screen viewport. Coordinates will be represented in world coordinates (meters). This is just like a video game.
  - The user will have the ability to zoom in using pinch to zoom and pan using their finger. This should be supported in the web app/browser.
  - The user will at any time be able to "snapshot" the field at that moment. This snapshot creates a "snapshot" record in the database that
  records each player on the field and their position in world coordinates. At a minimum we will capture all players and their positions,
  but we should plan the db structure to capture all anotations and other elements as well. The snapshot can be quickly named and saved as a child of the main
  playboard composition record. We'll want a camera/snapshot icon to create a snapshot. A shapshot name is auto assigned (date/timestamp), and
  the user can choose to override and edit the name. Most of the time, I expect the user to accept the auto-assigned name and allow the snapshot to quickly
  save with no further UI action.
  - The Composer will have a slider to distinguish between compositions that are static (drawings with annotations, etc.) versus
  dynamic (animated players following paths over time).
  - In dynamic/animation mode, the user will add a player to the field (or select one), hold them down for a "path" icon, then drag to create the path
  that the player will follow over the time.
  - The time is set by a slider, and can be changed on replay, etc.
  - In the same way, the user can add multiple players to the field and animate them in the same animation.
  - At any time, the user can select "Preview" to see the animation in action. They can then continue adding or editing it.


Data model and coordinates:
-Use normalized tables so compositions and snapshots are flexible and composable:
-Plays have an owner (user who created them)
-Should capture creating timestamp as part of the database record for view sorting by creation time.
-Plays can be edited and updated and eventually shared with the team.
-Plays have a name, description, and tags.
-Plays are saved in the database with a structure simulating file system "folders" for organization by the user.
-Plays are shareable entities that can be shared to a team's locker room (forum), public wall, etc. 
-Plays can be static "drawings" or short "animations" of players following paths on the field over a set time
to demonstrate a play or strategy.

Some thoughts on design. Note, these are just ideas not set-in-stone requests:
- playboard_snapshot(id, game_id, name, created_at, field_orientation, zoom, pan_x, pan_y, notes, tags[]).
- playboard_snapshot_player(snapshot_id, player_id, x_meters, y_meters, role_override, is_active, PRIMARY KEY (snapshot_id, player_id)).
- playboard_layer(id, snapshot_id, type, payload_jsonb, z_index) for drawings, cones, arrows, etc.

Some notes:
- Store world coordinates in meters with origin at one corner or the center;
- store field dimensions in a field_template table so different 
pitch sizes and age groups are supported.
- Distinguish logical formation vs. one specific snapshot: formation(id, team_id, name) plus formation_position(formation_id, role, x_meters, y_meters);
snapshots then reference a formation and override specific coordinates.

Rich anotation features
Drawing layer:
- Freehand and straight lines, arrows for runs and passes, dashed vs solid (e.g., sprint vs jog).
- Circles/rectangles to highlight zones.
- Store as vector objects (in playboard_layer) so they’re editable, not screenshots.

Equipment:
- Cones, small goals, mannequins, ladders, etc., to design drills; again, store as typed objects with coordinates.

Different board modes:
- Full pitch, attacking third only, set‑piece corner view, training ground layout.
- Each mode can be a field_template with its own coordinate mapping.

Configurable players:
- Name, number, role, maybe photo/icon so coaches can quickly see who’s who. I like a team-colored icon with the number and name
where a hold on the icon pops up a small card with more info.
- Easily add/remove players from the field and edit those on it.

Snapshots, versions, and reuse
-snapshots are first‑class concepts with history and reuse.
-snapshots are linked to the paren playboard composition, if one was saved 

Versioning:
- playboard_snapshot can have parent_snapshot_id and version so a coach can duplicate and tweak “4‑3‑3 high press v1 → v2”.

Tagging and organization:
- Text tags[] on snapshots: e.g., ["corner", "defensive", "u12"], and a free‑text notes field for coaching points.

Reusable libraries:
- Allow playboard compositions("plays") and snapshots to be attached to a game, if relevant. By default, they are stored 
in the user's playboard ("Plays") library so they can be shared whenever desired.


Export/sharing:
- Server‑side or client‑side render to PNG/PDF for sharing/printing.
- Sharable item: link to the resource can be shared by user in a team locker room, message from messaging system,
team calendar, discussion forum, etc.
- We need an icon to represent this type of sharable resource. Probably looks like a play drawn up on a board.

Interaction, multi‑device, and collaboration:
- You already have drag/drop, zoom, pan, tilt. To harden this for real‑world usage:

Device‑agnostic view:
- Persist camera/viewport per snapshot: zoom level, pan, orientation (which side is “up”), maybe per user.
- Use the world coordinate system exclusively in the DB; all “fit to screen” logic stays client‑side.

Offline‑first: THIS FEATURE IS IMPORTANT. The coach/user must have the ability to compose plays and "save them" locally on their device
so that they can be stored in the db later in case an Internet connection isn't available at the time the feature is needed.
- Local cache/queue of composed plays and snapshots; queue mutations with pending_sync flag and reconcile with server; the world
coordinate system makes merging simpler.

UX considerations and extras
Things that dramatically improve coaching usability:

Undo/redo stack for moves and drawings (store operations client‑side; persist only the final state on explicit save, or maintain operation log in a playboard_event table if you want full history).

Animation:

Multiple “frames” under one play: playboard_sequence(id, name) + playboard_sequence_frame(sequence_id, index, snapshot_id) to step through a movement.

Role‑aware snapping:

Optional grid or “role slots” for common formations; when you drag a player close to a slot, it snaps there, making it easier to keep shape clean.

Access control:

playboard_snapshot_acl(snapshot_id, user_id, can_edit) so assistants can propose plays, players can only view, etc.

Put together, you’d have:

A game‑engine‑style 2D tactical board using world coordinates and view transforms.

A normalized Postgres schema that treats snapshots, drawings, and sequences as composable data rather than one‑off blobs.

Coach‑friendly features (drills, annotations, exports, sharing, versioning) that match what dedicated tactical‑board products offer.



Item Sharing/Linking Concepts:
- The goal is to make most items that can be created and saved in the app shareable to individuals,
a team, or the public.
- We need some kind of "share table" that is a robust link table for different items to be shared/linked
to different entities (users, teams, public) through a variety of tools (email, discussion forum, calendar, etc)
with different permissions (view, edit, etc) and scope (public, team, individual).
- To facilitate this, we need to have owner/team FKs on created items.

- Team calendar.
- Team forum/discussion board for sharing posts, articles, photos, links to videos,etc.
- Team photo album.
- Team document library.
- Team playboard library.

- All entities and their data (documents, photos, videos except links, etc.) should be stored in the database.

- The top of the locker room should be an area for sticky notices and announcements, some generated automatically by

All of the entities created in these tools should be shareable as already described.

Player locker room tools:
